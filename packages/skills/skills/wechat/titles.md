# 工程公众号标题

为科技 / AI / 工程向公众号起标题。追求停滑与点击，但**标题必须被正文兑现**。


## Vault 落点（W2）

| 产物 | vault 路径 |
|---|---|
| Brief | `10-卡片盒/公众号/briefs/` |
| 成稿 | `10-卡片盒/公众号/drafts/` |
| 标题 / 审校 | `10-卡片盒/公众号/review/` |
| 排版 HTML | `90-附件/公众号/layout/`（**仅桌面本地工具写入**；模型不得直写 `90-附件/`） |

禁止双写 `/workspace/content-team`。笔记改动走 proposal → Apply。成品**禁止** `【待补】`；缺材料改为公开可核验事实或标明「假设」。


## 原则

1. 先建 **内容简报**（主题、读者、最硬事实、不能碰的红线），再批量出标题。
2. 至少覆盖 **6 种不同方法**，禁止 8 条同一套路。
3. 优先 **强实体锚定**（产品名、团队、具体系统），少硬塞假数字。
4. 禁用无依据的「刚刚 / 首个 / 独家 / 颠覆」；没实测禁止写「实测」。
5. 工程号少用阴谋揭秘腔；冲突对立必须有正文事实支撑。

## 字数与形态（经验校准，不是铁律）

- 目标 **15–28 字**（中文计）
- 一个强实体 > 多个弱实体堆叠
- 冒号、问句、反差可用，但每条主方法只用一个

## 推荐方法（工程向优先）

1. 实体锚定：`Claude Code + 具体动作`
2. 任务结果：`用 X 做完 Y，成本/时间变成 Z`
3. 亲测态度转变：必须有真实过程
4. 数字反差：数字必须来自正文
5. 反差转折：原以为 / 实际
6. 边界警告：`别在 … 场景用 X`
7. 对比选型：`A vs B，我们为什么留下 A`
8. 强时效：仅限真实刚发生的事

## 输出格式

对每个候选给出：

| 标题 | 方法 | 评分(1–10) | 风险 | 适合场景 |
|---|---|---|---|---|

然后推荐：

- **信息流点击款** ×2
- **信任/专栏款** ×2（更克制，适合工程号长期人设）
- **A/B 测试对** ×1

最后给用户 1 句改写建议：如何把口语标题改得更像本人。

## 红线

- 标题承诺正文没有的结论
- 伪造内幕、禁用、开战等戏剧冲突
- 纯情绪标题无信息缺口
